# AI Dream Job Engine 设计规格

状态：已批准（2026-10-11，已纳入 MCP App UI）

## 1. 产品定义

AI Dream Job Engine 是一个本地优先、开源的 Agent 插件，用来判断哪些 AI 岗位值得投入时间申请。这里的 “Dream Job” 同时受个人偏好、现实资格和可核验证据约束，不代表只寻找听起来理想的岗位。它的核心不是抓取岗位、改写简历或自动海投，而是一套证据驱动的价值判断框架，分别回答：

1. 用户是否想要这份工作；
2. 用户当前的资料是否足以证明自己适合申请；
3. 不匹配究竟是能力差距，还是简历没有呈现证据。

第一入口是 Codex。可复用能力通过 MCP 暴露，未来可以接入其他兼容 Agent。

## 2. 目标

- 提供开箱即用的 AI 岗位默认模板，不要求用户从空白开始设计标准。
- 允许用户以声明式方式定义事实字段、价值维度、关键词、权重、硬约束和阈值。
- 从简历证据和用户确认的信息建立 Candidate Profile。
- 输出可调整的推荐等级，并给出可追溯的 JD 和候选人证据。
- 分开计算偏好匹配和胜任力证据匹配。
- 分开显示能力差距和证据差距。
- 支持 OpenAI 和 OpenRouter 进行结构化提取与生成。
- 支持 JEV 生成 decision signals，但不让 JEV 替用户定义价值观。
- 允许用户选择是否从当前 Agent memory 导入补充背景，并在写入 Candidate Profile 前逐项确认。
- 能直接被 Agent 自带的自动化或定时任务调用，不在插件内部重复建设调度器。
- 个人资料默认保存在本地，任何有后果的动作都需要用户确认。
- 复用旧 AI Job Fit Analyzer 中经过验证的工程思路，但不修改旧仓库，也不复制个人数据和真实 JD 数据集。

## 3. 第一阶段不做什么

- 不做通用招聘网站或大而全的职业平台。
- 不做完整网站、浏览器插件或桌面应用。
- 不做云账号、跨设备同步、收费或订阅。
- 不做自动填写表单和无人确认的批量投递。
- 核心判断质量验证前，不做 Gmail 同步和自动岗位搜索。
- 不允许用户在价值规则中执行任意代码。
- 不把 Agent 记忆、模型推断或简历未提及的内容直接当作候选人事实。
- 不在后台默认持续同步 Agent memory。
- 不自建定时任务、通知中心或常驻调度服务。

## 4. 产品形态

用户安装一个 Agent 插件，插件包含：

- Skills：定义支持的工作流和证据规则；
- 本地 MCP Server：承载工具、数据、模型适配器和决策引擎；
- MCP App：作为第一版内置 UI，处理岗位判断、偏好配置、证据对比和确认。

Agent 是交互入口和信息发现者；本地 Candidate Profile 是用户确认后的事实来源；确定性决策引擎负责最终推荐。

### 4.1 Agent Automation 集成原则

- 自动化的创建、频率、暂停和通知策略由 Codex 或其他宿主 Agent 管理。
- 插件只提供可被自动化调用的工作流工具，不保存另一份调度配置。
- 自动化工具必须幂等，保存 `cursor` 或 checkpoint，重复运行不能重复创建岗位或状态事件。
- 每次运行统一返回 `no_change`、`updated`、`needs_review` 或 `failed`，并附带简短摘要和相关记录 ID。
- `no_change` 默认静默；只有发现值得关注的新岗位、状态变化、失败或需要用户确认时才通知。
- 自动化可以搜索、分析和同步状态，但不能越过用户确认执行投递。
- 第一阶段只建立这些接口约束；自动搜索与 Gmail 工作流仍在核心价值判断验证后实现。

### 4.2 MCP App 信息结构

MCP App 是面向日常使用的紧凑侧边栏，不是传统仪表盘，也不复制个人工作台。第一版只有三个一级视图：

- **岗位**：默认入口，显示待判断和已分析岗位；
- **我的标准**：编辑事实字段、价值维度、权重、硬约束和推荐阈值；
- **我的证据**：查看简历证据、用户确认事实和已确认的 Agent Memory 导入记录。

岗位列表优先显示岗位、公司、推荐等级、偏好分、胜任力证据分和最重要的未解决差距。选择岗位后，详情按以下顺序呈现：

1. 推荐等级和一句话结论；
2. 偏好匹配与胜任力证据匹配；
3. 硬性阻断；
4. 偏好差距、能力差距和证据差距；
5. 对应的 JD 证据和候选人证据；
6. `忽略`、`保留` 和 `补充我的证据` 操作。

首屏直接进入岗位队列，不设置营销页或欢迎页。Agent Memory 默认关闭，只能从“我的证据”主动发起预览，并逐条接受、修改或拒绝。任何事实或标准变化都通过本地 MCP Server 保存，并重新运行确定性计算；MCP App 不复制决策逻辑、不自行搜索岗位，也不管理定时任务。

第一版为符合条件的岗位预留 `待申请` 状态，但不提交申请。只有 `priority_apply` 且不存在硬性阻断或未解决证据差距的岗位，才能由用户主动加入待申请队列。

视觉采用白色、石墨灰、可信绿和警示红，颜色只表达状态和风险。界面避免卡片嵌套和装饰性大标题，优先保证侧边栏内的扫描、对比和确认效率。

## 5. 核心用户流程

### 5.1 首次配置

1. Agent 介绍默认 AI 岗位价值模板。
2. 用户导入简历或提供简历文本。
3. 系统提取候选人信息，并保留原文证据。
4. Agent 可以从用户授权的上下文中提出补充信息，但必须等待用户确认。
5. 用户调整偏好、硬约束、权重和推荐阈值。
6. 用户可以选择是否预览 Agent memory 中可能相关的经历和偏好。
7. 用户逐项接受、修改或拒绝候选信息，确认后才写入 Candidate Profile。
8. 用户配置 OpenAI 或 OpenRouter，并可连接 JEV。

### 5.2 Agent Memory 导入

Agent memory 是可选信息源，不是事实数据库：

1. 默认关闭，只有用户主动选择时才读取；
2. 用户可以限制导入范围，例如项目、技能、职业偏好或工作约束；
3. MCP Server 不直接扫描宿主的 memory；当前 Agent 只把授权范围内的候选信息和来源传入 MCP；
4. 系统先生成带来源的变更预览，不直接修改 Candidate Profile；
5. 用户逐项确认后，内容以 `user_confirmed` 保存，并保留原始来源；
6. 后续刷新只展示新增、变化和冲突，不静默覆盖已有信息；
7. 用户可以断开来源，并删除由该来源导入的信息。

### 5.3 分析岗位

1. 用户提供 JD 文本或本地可读来源。
2. 提取模型生成带 JD 证据的结构化事实。
3. JEV 对已配置的 decision questions 返回概率信号。
4. 规则引擎计算偏好匹配。
5. 规则引擎对照 JD 要求和候选人证据。
6. 系统分类硬性阻断、偏好差距、能力差距和证据差距。
7. 系统输出推荐等级与完整决策轨迹。
8. 用户修改配置或补充事实后，可以重新计算，不必重新解释无关数据。

## 6. 固定框架与用户自定义边界

### 6.1 产品固定

- 配置格式和版本管理；
- 证据和来源要求；
- 事实提取、模型判断信号和最终规则三层分离；
- 偏好匹配和胜任力证据匹配分离；
- 能力差距、证据差距、偏好差距和硬性阻断分离；
- 确定性的计分与推荐计算；
- 审计记录、模型元数据和人工确认状态；
- Agent 建议的信息在保存前必须由用户确认。

### 6.2 用户可配置

- 事实字段；
- 价值维度；
- 正向和负向关键词；
- 维度权重；
- 硬约束；
- 推荐阈值；
- 目标岗位、AI 领域、地点、薪资和工作方式。

自定义采用声明式配置。用户可以定义提取什么、如何影响决策，但不能通过配置执行任意代码。

## 7. 领域模型

### 7.1 Candidate Profile

每条候选人信息包含：

- 类型和标准化值；
- 来源类型：`resume_evidence`、`user_confirmed` 或 `agent_suggested`；
- 可用时保存原文引用或来源；
- 确认状态；
- 可选的时间和置信度元数据。

`agent_suggested` 在用户确认前不能影响推荐结果。

### 7.2 Fact Definition

每个用户定义的岗位事实包含：

- 稳定 ID 和名称；
- 定义；
- 数据类型：boolean、number、text、enum 或 list；
- 提取说明；
- 是否强制要求 JD 原文证据；
- 缺失时应标记 unknown，还是使用明确配置的默认值。

### 7.3 Value Dimension

每个价值维度包含：

- 稳定 ID、名称、定义和示例；
- 所依赖的 fact IDs 或 decision signal IDs；
- 权重；
- 可选的正向和负向关键词；
- 可选的硬性阻断规则；
- 计分方向与阈值；
- 解释模板。

### 7.4 Decision Signal

Decision signal 是模型生成的判断，例如 `product_facing`、`applied_ai`、`pure_infrastructure`。每条信号包含：

- 问题和版本 ID；
- 概率或校准后的置信度；
- 模型和供应商元数据；
- 可用时保存 JD 支持证据；
- 状态：available、unavailable 或 invalid。

Signal 只是价值规则的输入，不能直接决定最终推荐。

### 7.5 Decision Result

每个结果包含：

- 偏好匹配分；
- 胜任力证据分；
- 最终推荐等级；
- 偏好不符项；
- 硬资格阻断项；
- 能力差距；
- 等待用户确认的证据差距；
- 每一项对应的 JD 证据和候选人证据；
- rubric、prompt、model 和 result 版本；
- 是否需要人工确认。

第一版推荐等级：

- `priority_apply`；
- `apply_after_review`；
- `hold`；
- `skip`。

用户可以调整阈值，但等级含义和审计格式保持稳定。

## 8. 差距分类规则

- **偏好差距**：岗位与用户配置的偏好冲突，不代表用户能力不足。
- **硬资格阻断**：JD 明确要求与用户已经确认的事实冲突，例如地点或工作许可。
- **能力差距**：用户明确确认自己当前尚未满足该要求。
- **证据差距**：JD 有要求，但 Candidate Profile 没有足够证据判断是否满足。

简历没有写到的内容一律先标记为证据差距，不能直接判定为能力差距。系统应先询问用户，再决定是否更新推荐。

## 9. 决策流水线

```text
JD 输入
  -> 保留证据的结构化事实提取
  -> 可选的 JEV decision signals
  -> 偏好规则计算
  -> 候选人证据对照
  -> 差距分类
  -> 确定性推荐
  -> 解释与审计记录
```

模型职责：

- OpenAI/OpenRouter：结构化事实提取，后续也可用于申请材料生成；
- JEV：回答带版本的 decision questions，并输出概率信号；
- Python 规则引擎：计算权重、硬阻断、差距、阈值和最终推荐。

相同的标准化事实、Candidate Profile、signals 和 rubric 必须得到相同结果，不因调用它的 Agent 不同而改变。

## 10. MCP 与 Skill 接口

第一版只提供以下核心工具：

- `initialize_profile`：从简历生成待确认信息；
- `review_profile_claims`：查看待确认信息及来源；
- `confirm_profile_claims`：接受、修改或拒绝信息；
- `preview_agent_memory_import`：接收当前 Agent 在授权范围内提供的候选信息，并生成差异预览；
- `confirm_agent_memory_import`：确认、修改或拒绝导入变更；
- `disconnect_agent_memory`：停止后续读取，并选择是否删除已导入信息；
- `get_rubric`：读取默认模板和用户覆盖项；
- `update_rubric`：应用通过校验的声明式修改；
- `analyze_job`：分析一个 JD 并保存结果；
- `recompute_decision`：配置变化后重新运行确定性计算；
- `get_decision_trace`：查看结果背后的证据和因素；
- `list_analyzed_jobs`：列出本地分析记录。

Skill 负责引导 Agent 收集缺失信息、请求确认，并避免把推断说成事实。MCP App 只处理岗位判断、rubric 编辑、信息确认和证据比较，不扩展成通用仪表盘。

## 11. 本地数据与安全边界

- 使用本地 SQLite 保存 rubric、Candidate Profile、岗位结果和审计记录。
- 不复制旧仓库的真实 JD 数据集或未跟踪的个人岗位库。
- API key 不进入数据库和仓库；使用环境变量或宿主支持的密钥存储。
- 默认只把公开 JD 发给 OpenAI、OpenRouter 或 JEV；JEV 不接收 Candidate Profile。
- 事实提取与最终匹配分离：外部模型提取 JD，Candidate Profile 对照和推荐计算在本地完成。
- 完整简历、Agent 原始 memory 和邮箱正文属于 restricted data，插件不得默认发送给外部供应商。
- 简历可以由当前 Agent 在宿主权限范围内提出候选信息，或由用户手工填写；若用户选择远程模型解析完整简历，调用前必须显示供应商、发送字段和用途，并单独确认。
- 后续申请材料生成只能发送用户明确选择的 Candidate Profile 条目，不能默认发送整个本地画像。
- 每次模型调用只发送完成任务所需的最少字段，并在本地审计记录中保存数据类别，不保存密钥。
- 记录哪个供应商接收了哪一类数据。
- 未经用户明确连接或提供，不读取邮箱、Agent memory 或本地文件。
- Agent memory 导入默认关闭，只能由用户主动触发，并在保存前显示来源和变更预览。
- 不把不同 Agent 的 memory 视为自动一致；每个来源都单独记录，冲突交给用户确认。
- 默认不收集遥测；日志对简历、memory、邮箱和密钥字段做脱敏。

数据分类：

- `public_job_data`：公开 JD、公司和岗位信息，可按用户配置发送给模型供应商；
- `selected_candidate_claims`：用户明确选择的候选人条目，只能在指定任务中发送；
- `restricted_personal_data`：完整简历、原始 Agent memory、邮箱正文和密钥，默认只留在本地或当前宿主上下文。

## 12. 可靠性验证

第一个里程碑是 20 个真实 JD 的决策质量验证，而不是扩大功能。

每个 JD 都要先记录用户的独立判断，再展示系统结果。评估：

- 排名前五的岗位是否真的值得申请；
- 推荐等级一致性；
- 硬性阻断判断是否准确；
- 偏好差距解释是否正确；
- 能力差距和证据差距是否分对；
- 是否出现无来源的候选人信息或 JD 判断；
- 相同标准化输入重复运行是否稳定；
- 与人工筛选相比节省多少时间。

MCP App 的第一版可用性验收标准：

- 用户能在 30 秒内判断一份 JD 是否值得继续查看；
- 用户能明确区分偏好不符、硬性阻断、能力差距和证据差距；
- 所有影响推荐的个人事实都经过用户确认；
- 关闭并重新打开 Codex 后，本地岗位、标准、证据和分析记录仍然存在；
- UI 显示的推荐、分数、差距和证据与同一分析记录的 MCP 工具输出一致。

一致不等于客观准确。所有分歧进入 failure-review 数据集，用来修改 rubric 或提取逻辑。只有核心结果达到用户在真实求职中愿意依赖的程度，才进入自动搜索、Gmail 同步和材料生成阶段。

## 13. 与旧项目的迁移边界

旧 AI Job Fit Analyzer 保持不变。规格批准后，新项目可以选择性重写或适配：

- Pydantic 风格的结构化契约；
- 证据切块和原文引用校验；
- 与供应商无关的模型调用边界；
- 确定性决策函数；
- 运行记录和失败日志思路；
- 聚焦的单元测试模式。

新仓库不得复制：

- 湾区地点和个人目标活动等硬编码偏好；
- 个人岗位库或真实 JD 数据集；
- 密钥、日志、缓存和虚拟环境；
- 旧 Git 历史；
- 把旧项目的临时标签描述成准确率的结论。

## 14. 延后扩展

20-JD 里程碑通过用户审阅后，再分别设计：

1. AI 岗位自动搜索与去重；
2. 申请材料准备；
3. 用户确认的待申请队列；
4. Gmail 后台状态同步，但不内嵌邮箱；
5. 其他 Agent 宿主；
6. 可选云同步或辅助网页。

这些扩展必须继续使用同一套 Candidate Profile、rubric、证据边界和决策轨迹。
自动搜索和 Gmail 同步应作为宿主 Agent automation 调用的粗粒度工作流提供，而不是在插件内部运行独立 scheduler。

### 14.1 自动投递边界

自动投递按三个阶段演进：

1. 自动准备针对岗位的简历、申请答案和材料清单；
2. 用户查看公司、岗位、简历版本和回答内容并确认后，由 Agent 填写和提交；
3. 仅在用户明确授权特定来源、推荐等级、每日上限和停止条件后，才评估无人值守投递。

默认停留在第二阶段。系统不能因为自动搜索发现岗位就直接提交；不能为完成投递绕过验证码、登录限制或平台访问控制。每次投递必须保存岗位、材料版本、确认记录、提交时间、结果和来源。任何硬性阻断或未解决证据差距都会禁止进入投递动作。

网页登录复用用户当前浏览器中的会话，插件不接收或保存账号、密码、验证码和浏览器 Cookie。Agent 在打开申请页面后先检查登录状态；如果需要登录、二次验证或验证码，任务保存非敏感进度并进入 `needs_login`，由用户在浏览器中完成验证，再从原任务继续。登录过期时同样停止并请求用户处理，不能尝试绕过访问控制。不同公司的独立招聘系统分别判断登录状态，不承诺一次登录覆盖所有网站。邮箱连接使用 OAuth，不使用邮箱密码。

## 15. MCP App 设计阶段验收标准

- 旧仓库没有因新项目发生任何变化；
- 现有本地核心、MCP 工具和隐私边界保持不变；
- 用户确认 MCP App 的入口定位、三个一级视图、岗位详情顺序和操作边界；
- 在用户确认本次规格增补前，不创建 MCP App 实现计划或 UI 代码。
